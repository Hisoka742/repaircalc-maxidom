# Методика оценки привязки товаров к видам работ

Документ для согласования с организаторами. Что измеряем, на чём, по каким правилам, какие пороги
и как проверить результат самостоятельно одной командой.

## 1. Задача и таксономия

Для каждого товара каталога определяем **все виды ремонтных работ**, в которых он участвует
(многометочная классификация), и роль товара: материал, инструмент или расходник. Справочник —
42 вида работ в 9 этапах (подготовка, черновые, стены, полы, потолки, электрика, сантехника,
двери и окна, общие), `src/maxicalc/knowledge/taxonomy.yaml`; определения, правила включения и
разбор спорных случаев — `docs/TAXONOMY.md`. Типы помещений и свойства товара остаются
отдельными независимыми признаками. Пустое множество («к ремонту не относится») — допустимый ответ.

## 2. Правила разметки (кратко)

1. Вид работы ставится по **применению**, а не по словам в названии.
2. Товар получает **все** работы, где нужен: грунтовка — грунтование, покраска, укладка плитки,
   поклейка обоев, шпаклевание.
3. Инструмент и расходник наследуют работы основного применения; универсальный инструмент —
   `general_assembly` и 2–6 ключевых работ.
4. Товары вне ремонта — пустое множество.
5. Ячейка разметки: `id;id`, `none` (ничего не подходит), `=` (принять подсказку, только в строках
   с подсказкой).

## 3. Построение тестового набора

- Источник — **официальный набор организаторов** `products_final.json` (88 790 товаров всех
  отделов магазина, 2 375 категорий-листьев, дерева категорий нет; лежит в `data/raw/`, в репозиторий
  не попадает). Прежний YML-фид остаётся запасным источником и даёт дерево категорий
  (`knowledge/category_lift.json`).
- **Ремонтная часть, 640 товаров**, стратификация по категориям второго уровня: квота пропорциональна
  корню из размера категории (каждая категория представлена, крупные не заглушают малые). «Ремонтность»
  — по карте категорий `knowledge/category_work_map.csv` (`docs/CATEGORY_MAP.md`).
- **Неоднозначная часть, 100 товаров**: 52 — обязательные квоты по семействам, названным
  организаторами (саморезы, грунт, уголки для плитки, монтажный клей, профили, пена и герметики,
  дюбели), остальные — по оценке неоднозначности (много видов работ, смешанные категории,
  расхождение правил и модели, слово работы в названии без метки), не более 4 с категории.
- **Негативы, 110 товаров** из неремонтных отделов (сад, посуда, одежда, мебель, химия): правильный
  ответ — «нет видов работ»; показатель — доля негативов, получивших вид работ.
- **Разделение dev / test** по хэшу артикула (40 % test): по test ничего не настраивается. Пороги
  по видам работ подбираются только на dev; отчёт — по test.
- Файлы: `scripts/make_worktype_gold.py` создаёт 4 листа по 258 строк (60 общих + 198 своих) и
  `manifest` (всего 850 уникальных товаров).

## 4. Согласованность разметчиков

60 общих строк (40 стратифицированных + 20 неоднозначных) получает **каждый** разметчик, **без
подсказок системы** (чтобы подсказка не завышала согласие). Остальные строки делятся поровну, с
подсказкой правил. Считаем (`scripts/merge_worktype_gold.py`, `eval/gold/AGREEMENT.md`):

- κ Коэна для каждой пары разметчиков по всем ячейкам (товар × вид работ), среднее по парам, κ по видам работ;
- α Криппендорфа (номинальная, бинарная, любое число разметчиков).

Пороги: ≥ 0,8 — надёжно; 0,67–0,8 — условно; ниже — правила разметки дорабатываем и размечаем заново
спорные виды работ. Итог для общих строк — большинство голосов (строго больше половины); ничья по
виду работы отправляет строку на решение человека, пока она не решена, в золотой набор не входит.

**Статус: людьми размечено 0 строк, согласованность не измерена** (листы готовы, разметчики не
приступали). Пилот «один разметчик — LLM» (`eval/gold/pilot_llm_labels{,_b,_c}.csv`, метка
*NOT human*) служит только для отладки правил; его числа в `docs/CATEGORY_MAP.md` помечены PILOT.
Разметчик пилота писал и правила, поэтому честной считается только оценка **первого прогона на
свежем наборе**, до доработки правил.

## 5. Метрики и пороги

| метрика | роль | порог |
|---|---|---|
| micro-F1 по всем (товар, вид работ) | основная | цель ≥ 0,8, ориентир ≥ 0,9 |
| macro-F1 | вспомогательная | отчёт |
| P / R / F1 по каждому виду работ | диагностика | отчёт |
| sample-based F1, Hamming loss, доля точных совпадений | вспомогательные | отчёт |
| те же метрики на неоднозначной части | отдельно | отчёт |
| MAP@10, nDCG@10 по виду работ («какие товары нужны для работы X») | ранжирование | отчёт |
| «семантика, не буквы»: пары, где в названии нет ключевого слова работы | отдельно | отчёт |
| воспроизводимость: обучение на части категорий, оценка на отложенных | `make reproduce` | отчёт |

Системы сравниваются на одном test: только правила, только модель, правила + модель. Реальные
числа появятся только после разметки; сейчас в отчётах помечены **СИНТЕТИКА/SILVER** результаты на
метках-правилах (297 отложенных категорий официального набора: micro-F1 0,857, macro-F1 0,726).

## 6. Как проверить на своих товарах (одна команда)

```bash
uv run python scripts/eval_worktypes.py --gold <ваш_файл_меток.csv> --catalog <ваш_каталог.(xml|csv|xlsx|json)>
```

Файл меток: `sku;works;split;group`, где `works` — id видов работ через `;` или `none`, `split` —
`dev`/`test`, `group` — `stratified`/`ambiguous`. Каталог читается любой из адаптеров (YML, CSV,
XLSX, JSON, также `.gz`). Результат: `eval/WORKTYPES.md` (таблица систем, неоднозначная часть,
«не по буквам», ранжирование, F1 по каждому виду работ).

Полный цикл с нуля на ноутбуке: `uv sync && make reproduce` (фид → правила → обучение на части
категорий → оценка на отложенных → время и ресурсы в `eval/REPRODUCE.md`).
Загрузка каталога и разметка через API: `POST /api/v1/catalog/upload`, очередь проверки
`GET /api/v1/catalog/upload/{job}/review`, новый товар `POST /api/v1/catalog/work-types/classify`.

## 7. Ограничения, которые мы не скрываем

- Правила (≈ 200 шт.: категорийные `work_rules.yaml` и поэлементные `work_refine.yaml`) написаны нами;
  модель обучена на метках правил (слабый учитель) и на золотом наборе, когда он появится. До появления
  человеческих меток точность относительно людей неизвестна.
- Слой поэлементных правил доводился по ошибкам пилотных наборов A и B; наборы доработанных
  семейств (in-sample) нельзя цитировать. На свежем наборе C до доработки выигрыш над категорийной
  картой на неоднозначных строках составил всего +0,07 micro-F1.
- Часть решений таксономии спорна и ждёт людей: СИЗ, универсальный грунт, декоративные профили.
- В данных организаторов встречаются ошибки полей (например, у некоторых товаров параметры «семена»
  и «пена монтажная» перепутаны; бренд пуст у серии PLITONIT; расход без единицы). Нормализация
  описана в `docs/DATASET_REPORT.md`; исходный текст значений сохраняется.
- Временного среза в данных нет, поэтому проверка на «новых» товарах сделана по отложенным категориям
  и по пилотным наборам свежих товаров, не по времени.
